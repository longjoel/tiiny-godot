# Tiiny Godot workspace assistant

This fork is exploring a Godot-native assistant powered by a Tiiny device. The goal is to turn a request into workspace operations: inspect scenes and resources, use Godot's built-in features, generate and import assets when needed, and report what changed. Think of it as a powerful, context-aware editor macro. Gameplay GDScript is a fallback when built-in tools cannot reasonably provide the requested behavior. Internal asset-building jobs may use disposable Godot generator scripts outside the editor process.

The integration is an **early prototype**. The workspace operations and undoable scene-editing workflow are a design direction, not finished features. See [WORKSPACE_ASSISTANT.md](WORKSPACE_ASSISTANT.md) for the design and first milestone. The sequenced implementation backlog and current work are in [plan/README.md](../../plan/README.md).

## What exists today

- **Prototype bodies:** for simple colored-rectangle games, `add_rectangle_body` creates a CharacterBody2D, StaticBody2D, RigidBody2D, or Area2D with a Polygon2D visual and a matching RectangleShape2D collision in one undo action. The prompt steers these requests to it and away from image generation; attach movement/jump/gravity with a small GDScript controller. A sprite-from-image path remains available when an actual texture is wanted.
- **Runtime verification:** `verify_scene_runtime` loads a saved scene in a headless probe outside the project, simulates physics frames and named input actions (for example `ui_accept` for jump), and reports measured body motion plus `scene_loads`, `no_errors`, `gravity`, `lands`, and `jump` checks. A failed check is returned as evidence with `passed: false`, not as a tool error. It needs `Advanced > allow_shell_commands` and per-run approval because it executes project scripts, and it never edits the scene or project.
- **Safe script check:** `check_gdscript` compiles a snippet in memory with no file, process, scene edit, or execution, and returns the real parse or compile message with its line plus the base class, methods, signals, and optional node-class compatibility. It needs no approval. A leading `@tool` annotation is ignored so a static initializer cannot run, and preloading another GDScript is refused because that can run its static initializer; asset preloads may still be resolved.
- **Built-in docs:** `lookup_docs` reads the compiled Godot class reference offline: class summaries, exact method/property/signal/constant signatures and documentation, partial member matches, and class-name search. It resolves through the editor's GDScript language-server workspace without a network client and is read-only.
- **Existing assets:** `find_assets` inventories project images, models, audio, scenes, scripts, and resources, including image dimensions, average color, alpha, byte size, import state, and up to five referencing scenes/scripts. The request context also includes a compact `Assets:` summary. The prompt tells the model to reuse an existing path before generating or importing a duplicate. This is deterministic metadata, not image-model classification.
- **Chat images and views:** paste an image from the clipboard or attach a project image; up to four bounded PNGs are stored under `user://` and sent as OpenAI-style `image_url` parts. Conversations, job parameters, and traces keep attachment references rather than base64. Requires an `Image-Text-to-Text` coding model. `capture_scene_view` captures the editor's 2D/3D view; `capture_player_view` reports that an external game window cannot be captured, so paste an OS screenshot of the player instead.
- **Visual classification:** `classify_visual` prepares a bounded texture or captured scene, queues a vision request through the existing asset job, and returns a description plus labels as a tool result. Results are cached by image hash, prompt, and model; cache hits skip inference. It uses the coding model and never switches to the image-generation role.
- **Scene edit reliability:** `apply_editor_transaction` accepts `name`, `path`, or `target` for created nodes; `parent`, `target`, and `owner` accept node IDs, names, or planned scene paths. Vector2/Vector3 properties accept arrays, `{x,y}`, or strings like `Vector2(200, 200)`; texture properties accept `res://` image paths. Missing classes are inferred from `value`/`target`/`name`/`path` when they name a node class, with safe name hints (Sprite2D, CollisionShape2D, StaticBody2D, CharacterBody2D, Camera2D, Label); generated IDs are de-duplicated. `set_property` accepts `parent` + `path` as target/property aliases. Successful scene edits auto-save by default (`Advanced > Auto-save scene`) so the next transaction is not blocked by a dirty scene; disabling it requires an explicit `save_edited_scene` between transactions. `append_job` rejects scene-edit operations with a direct instruction to call `apply_editor_transaction` instead.
- **Tool budgets and retries:** normal turns allow 100 tool rounds / 200 calls by default, configurable under Advanced (`0` disables the explicit limit, with a 1000/5000 safety ceiling); task jobs keep a 10/14 work budget plus a `submit_result` wrap-up. Reaching a budget queues a final tool-free summary step instead of stopping with a limit error. Repeating the same tool call consecutively, or three times without progress, also triggers the summary; a mutating call resets that repeat guard. This includes identical failed calls, which no longer stop the turn. Prose followed by an inline `<tool_call>` block is executed; only a block-free marker is treated as an unstructured stop. Every budget stop, repeated-call stop, and failed turn writes a JSON trace under `res://.tiiny/logs/traces/` and records its path on the job; **Copy trace** copies the current turn's prompt, messages, tool calls/results, ledger, counters, and failure reason for diagnosis. A failed chat retry carries the original prompt, prior messages and tool results, and a labeled failure note into the new attempt; jobs created before this behavior also get a synthesized retry context.
- **Tiiny Chat:** a conversational side dock with a message history and a single input box. Every request is dispatched directly to the coding model; there is no pre-answer classification request. Each turn sends the edited scene, the selected node paths/types, key project settings (project name, display size, stretch mode/aspect, main scene, renderer), and the captured root `AGENTS.md` project instructions when present. The model's `reasoning_content` is shown as a collapsed **Reasoning (N chars)** block under each response; click it to expand. **Advanced / Log chat** appends prompts, reasoning, tool calls, and responses to `res://.tiiny/logs/chat.log` (rotated at 5 MiB), and **Advanced / Model thinking** toggles the model's reasoning mode. The active conversation lasts for the current editor session; accepted chat jobs retain their submitted context and result in the project queue history. Replies are plain text: the dock has no Markdown renderer or editor, so prompts ask the model not to use headings, bold, tables, or fenced code.
- **Turn steps (story 20):** a queued chat turn is split at model-round boundaries. Each step is its own FIFO `chat_turn` job with its own time budget; when the model asks for another round, the queue commits the completed result and its continuation at the tail in one persisted transition. The result records `continued` and the next job ID. The continuation restores the turn's messages, round counters, ledger, and scene context from its job parameters, so it can resume after other queued work or an editor restart. A crash before the transition leaves the parent interrupted for reconciliation and creates no continuation. A failure in any step still stops dispatch. A response that hits the output limit is retried up to twice with a concise continuation prompt instead of stopping the turn, and the model's prior reasoning text is not sent back in the conversation. A `generate_image` call is handed off to its own image job; the imported result and any remaining calls in the model response return through a queued continuation. A failed or interrupted image job stops the queue for review. Headless and shell tools still run inside the chat step and are not yet separate jobs.
- **Prototype tools:** the model can inspect the edited scene and create a rectangular `CollisionShape2D` with an owned `RectangleShape2D` as one undoable recipe, create a new GDScript file as a justified fallback, or request experimental image generation. Workspace tools are advertised only when their scene and model prerequisites are available; the tool list and result ledger come from one registry. The image adapter has passed loopback PNG/import checks and live Tiiny image generation; image-model scheduling and response handling are described below. Generated images are saved in `res://tiiny_generated/`. The script tool requires a fallback reason, validates GDScript, and refuses to overwrite existing files. Tool results are structured and returned to the model for up to six model/tool rounds and eight calls per turn.
- **Workspace coding mode (story 18):** **Tiiny AI > Advanced > Tool Mode** selects **Editor** (default), **Workspace**, or **Hybrid**, and the chat dock shows the active mode. Workspace and hybrid expose root-confined `list_files`/`read_file`/`search_text`/`file_info`, SHA-256-guarded atomic `write_file`/`apply_patch`, approval-gated create/move/delete, read-only `git_status`/`git_diff`/`git_log`, and `run_godot_headless`; hybrid also keeps the typed scene/resource/debugger/asset tools. Creating a script through `create_gdscript` also requires approval. File edits are not scene-undoable and never appear in scene Undo: action cards show the affected file, a `File change · not scene-undoable` note, and **Review diff**. Writes, moves, and deletes re-check the hash near commit; an external edit in the final check-to-commit window can still be lost. New files and move destinations use no-overwrite hard links and fail if the filesystem does not support them. Git excludes known credential paths and redacts common token formats, but cannot identify every secret in an allowed file or commit message. Dirty scene tabs refuse file edits and reloads; a reload that would discard unsaved changes requires an explicit dialog decision. Host shell commands and headless project scripts are disabled unless **allow_shell_commands** is enabled, and each run still asks for approval because project scripts are host code. File mutations reject targets with unsaved script-editor buffers as well as dirty scenes.
- **Project settings:** `get_project_settings` reports display size, stretch mode/aspect, renderer, main scene, project name, and default gravity. `set_project_setting` validates one allowlisted setting and saves `project.godot`; it is a project-wide file change, not a scene undo action. The chat context already includes the current display size and stretch settings, so the assistant does not have to ask for them.
- **Resource experiment:** the Create New Resource dialog accepts an AI description for `ConvexPolygonShape2D`; leaving it blank performs normal creation. The returned points are converted to a convex hull. Other resource types are not yet supported by this dialog.
- **Script attachment:** typed scene transactions can attach an existing GDScript to a compatible owned node or the edited scene root. `attach_script` attaches an existing file; `create_and_attach_gdscript` validates a new script and target before asking to create the file, rechecks the scene after approval, and then attaches it; it can also create a compatible node under the target. If the requested file already exists with identical content, `create_and_attach_gdscript` attaches it instead of failing. The new file is a separate, non-undoable file effect; the scene change is one undo action. If attachment fails after file creation, the result reports the remaining file. An incompatible script base class is rejected before the scene changes.
- **Image-to-3D references:** the queued 3D generator accepts a project PNG reference up to 20 MiB and 4096 pixels per dimension. It validates and decodes the image before submitting it to Tiiny; denied project paths and symlinks are rejected.
- **Queued image generation:** an `asset_generate` job with kind `image` generates and imports a PNG using the selected image model. Image jobs submitted by the assistant can load that model on demand and restore the configured warm set afterward, with both transitions recorded on the job. A request with an unknown remote outcome stops for recovery rather than starting restoration. Its completed job result includes an artifact ID and SHA-256. A later image-to-3D job may use that `image_artifact_id`; it verifies the producer completed earlier in the FIFO and that the image still matches its recorded hash. Image-to-3D and speech models must be loaded or scheduled before their jobs run. The image remains available if the downstream job fails.
- **Planned task trees:** the coding model can submit a 1–3 task `submit_plan` for a larger request. Tasks run serially as ordinary `chat_turn` jobs in dependency order; each returns a structured result through `submit_result`. The plan's continuation is deferred and appended only when every task's latest attempt is resolved, so a user-confirmed retry or planner proposal runs before the join. A normal task failure is contained: independent siblings and unrelated queued work continue, while dependents wait. Failed tasks appear in Needs attention with **Fix task**, offering an edited retry, **Skip task**, **Cancel plan**, and **Ask planner**. Planner guidance is a proposal the user must confirm. Unknown device or process outcomes still stop dispatch. The plan result reports per-task outcomes and a completed, partial, failed, or cancelled rollup.
- **Device settings:** editor settings include the connection, SDK path, device address, model roles, and warm-model choices. The Models screen reads the live catalog, loaded state, allocation budget, and SSD capacity. A stale or unavailable snapshot dims the capacity bars and blocks Check Config and Apply until Refresh succeeds; unknown capacity is shown as unknown, never zero. Role pickers list only capability-compatible models, explain when a role has no compatible catalog model, and label installed versus downloadable choices. Changes are staged in a draft, checked against refreshed data, and submitted to the Jobs queue with Apply; unapplied edits are visibly marked. Model operations show the current action, percentage, and elapsed time in the panel, and per-row Info opens a resizable, copyable dialog. Model operations run in queue order and stop for review if their device outcome is uncertain. If another compatible coding model is already loaded, the editor adopts it as the scripting model instead of restoring an older saved selection; queued restores for the replaced selection are cancelled, and running restore work adopts the loaded model without switching. When no compatible coding model is loaded, the previously applied coding model is restored on startup or reconnect, which may download or load that model.
- **Output:** request and model-management status is written to Godot's Output panel as well as the dock's status line. The edited scene and selected nodes are always sent with chat requests; there is no screenshot input.
- **Jobs (experimental):** the bottom panel is a scheduler board with Queued, Running, Needs attention, Completed and Failed columns; cards move left to right as the FIFO queue advances. Running cards show the live stage and elapsed time. Queued cards can be cancelled individually, and the Queued column has **Cancel all**; cancelling before start does not stop later queued work. Failed cards can be retried (back to Queued) or cleared; completed cards can be cleared, individually or with the column action. Clearing hides the card while retaining the queue record. Interrupted device work appears under Needs attention: **Skip** abandons it after a confirmation and releases the device lease, while scene attachments offer **Check** for scene-specific recovery. Double-clicking a card opens a resizable job-details window with selectable, copyable text. Jobs are submitted by chat (reviewed tree images, follow-ups, scene attachments), the Create Resource dialog, and model configuration or restoration; the panel has no manual tree/attachment entry controls. The reviewed tree worker can request one additional tree job at the queue tail when a follow-up destination is supplied, and the generated image is imported before the job completes. For interrupted model operations, **Check** reads and records the current device state without retrying; the remote operation may still be changing. An uncertain model operation or inference request also blocks other projects using the same Godot data directory until it is explicitly acknowledged. When the uncertain record belongs to another project, the Jobs panel shows **Acknowledge device**; it clears the shared record only after a confirmation that the remote outcome is unknown. Clearing a failed job also clears a matching uncertain record. A failed or interrupted job stops later work; retry or skip requires a separate resume. Clearing a failed job resumes the queue when other jobs are waiting, and submitting a new chat resumes a paused queue. Queue history is stored under `.tiiny/jobs/`; per-attempt working files are under `.godot/tiiny/asset_jobs/`. This initial implementation uses Unix file locking and hard links, so it is unavailable on Windows and requires the working files and destination to share a filesystem. Queued specialized-model scheduling is implemented. Headless Godot and host commands invoked from chat are pre-approved when the model requests them, then run as their own `shell_exec` jobs with a bounded timeout and owned process group; the job revalidates the setting and approval at dispatch and records the process id. A known failure resumes the turn with the actual error after the stopped job is cleared. An interrupted shell job is never retried automatically: its process may still be running, the details show the recorded pid, and **Skip** resumes the turn with an unknown outcome.

Story 01 establishes a verified prototype baseline: real Tiiny chat and polygon generation/save/reopen, native resource/node dialog regressions, process cleanup, HTTP failure recovery, and displayed editor checks. Story 04 additionally verifies one real download-only model Apply with device progress and an unchanged warm set. This does not complete the planned workspace tools or validate real loads/unloads or generator quality. See [story 01 acceptance evidence](../../plan/evidence/01-completion.md) and [story 04 acceptance](../../plan/evidence/04-acceptance.md).

An interrupted attachment leaves the queue stopped. Open the intended scene, resolve any unsaved changes, and use **Check recovery** in Jobs. The check can verify an unchanged scene or a saved attachment created by the job; an ambiguous or modified scene remains stopped. A verified unchanged scene still requires **Retry** or **Skip**, followed by **Resume**.

Chat turns and Create Resource polygon inference use the FIFO queue. Chat prompts, captured scene/selection context, conversation snapshots and responses are retained in `.tiiny/jobs/queue.json`; API keys are resolved at execution and are not intentionally stored by the queue. Chat, resource inference and model-management requests share a device lease across editor processes using the same Godot data directory. If an in-flight request times out or is cancelled, its remote outcome is treated as unknown and the queue remains stopped. For model operations, Check records a read-only device observation; it cannot prove the remote operation stopped, and the user must explicitly acknowledge the uncertainty before resuming. A resource-dialog callback cannot survive an editor restart, but the validated polygon points remain in the job result.

## Setup

1. Install and authenticate the [Tiiny SDK](https://dev.tiiny.ai/) and connect the device. Build and launch this fork's editor, then open a project.
2. In **Editor > Editor Settings > Tiiny AI > Advanced**, set the API URL and API key. If the key is empty, the editor uses `TIINY_API_KEY`, then the authenticated SDK configuration. The password field masks the value but Editor Settings stores it on disk.
3. In the same **Advanced** section, set the SDK CLI path and, optionally, a device address. A blank address uses the SDK's currently selected device. The default `http://openai.api.tiiny/v1` URL is routed through that same bound device with the required Host header. A custom API URL must use the bound device address. Also choose **Tool Mode** (`editor`, `workspace`, or `hybrid`) and leave **allow_shell_commands** off unless you intend to approve host commands or headless project scripts. Both Models and Advanced appear in the normal settings view without enabling Godot’s global Advanced Settings toggle. Existing Connection and Device values migrate automatically; any already configured Advanced value takes precedence.
4. Open **Tiiny AI > Models** and select **Refresh**. Capacity bars appear above one model table. Each row shows context, throughput ("Not measured" until a benchmark exists), catalog download size, NPU allocation, desired **Keep loaded**, and actual installed/loaded state. Each row's **Info** button opens its description and capabilities. Unassigned installed models appear as additional rows in this same table.
5. Choose task models and the scripting context budget. Scripting requires a text model with declared tool-use support and is always kept loaded. Optional model choices are filtered by catalog type; descriptions help distinguish specialized variants. Role selection alone does not establish generation quality.
6. Select **Check Config**. Review projected capacity and the ordered download/unload/load plan; **Details** shows staging forecasts and warnings. **Advanced headroom** contains optional minimum free-capacity settings. Changing them invalidates the check; they affect plan validation rather than reserving device storage or allocation directly. Check Config does not mutate the device. Apply stays disabled on incompatible selections, unknown required capacity, insufficient headroom, or a protected coding-model switch that cannot fit both old and new models.
7. Select **Apply** to queue the checked plan; it is revalidated when the job runs. Draft edits invalidate the check; checks expire after 60 seconds. Inventory changes require a fresh review. Preferences are saved only after the result is verified. No restart is required.

Output records download percentages reported by the device and elapsed time, polling approximately every three seconds while the command runs. Repeated percentages are limited to one update per ten seconds. Other model operations forward SDK percentages when present. Terminal escape codes and arbitrary SDK output are filtered. A percentage is progress only; operation completion still requires device verification.

This fork assumes exclusive use of the configured Tiiny. Applying the warm configuration can unload models used by other applications. A failed download or load may leave a partial configuration; check Output and retry. Authentication and connection failures are reported separately and clear the last device snapshot. Readiness is based on a device snapshot bound to the configured address and credentials, and expires after 60 seconds; chat and resource requests revalidate it automatically when stale instead of requiring a manual Refresh, and Refresh remains available. The manager checks the saved coding model periodically and restores it when it can do so without unloading another model. Queued specialized jobs can schedule on-demand model swaps with coding-model protection; headless and shell tools invoked by chat still run within the chat step. Shutdown stops the owned SDK process tree; completed remote effects are not rolled back and must be rechecked. The current SDK adapter requires Linux `script` and `timeout` commands for model operations. A failure stops further operations and refreshes the observed state; it is not an atomic rollback. The planner never deletes installed models to free storage.

## Capacity and context

Tiiny's 100-unit model allocation budget is distinct from physical NPU RAM and compute utilization. The planner uses `/api/v1/models/npu/status`, the catalog's per-model units, and `/api/v1/sys/storage`. It counts each selected model once, retains unattributed allocation, and reserves configurable NPU units (default 5). SSD preflight includes missing downloads, a conservative largest-download staging allowance, and a reserve (default 2 GiB). These are admission checks with explicit allowances, not guarantees about unknown runtime allocations or archive expansion. Every operation is verified against the device.

**Context** is currently a client-side chat request budget. Selecting a coding model defaults the budget to that model's catalog maximum (for example 262,144 tokens for Qwen3.6), and the picker can lower it. The SDK exposes no load-time context-allocation flag, so a smaller choice does not reduce the NPU footprint shown. Chat conservatively budgets text using UTF-8 bytes plus framing/output allowance. Oversized requests are rejected rather than silently truncating context. **New chat** clears the model context and the dock history; completed results remain in the project queue. Actual tokenizer-based budgeting and runtime context reconfiguration remain future work. The table does not invent token/s measurements.

**Advanced / Request timeout** (seconds) limits each chat turn. Set it to `0` to disable the client timeout and job deadline entirely for slow models; the request and queue step then wait until the response or an explicit cancel. Model operations use their own long grace and a stall check.

Tiiny AI has two settings sections: **Models** for model configuration and **Advanced** for connection, device, prompt, and request limits. There are no separate Tiiny Assistant or Tiiny Models settings tabs.

## Context and instructions

Every chat request sends the edited scene path and root name plus the selected node paths, classes, and basic properties (2D transform, sprite texture/centering, Control rect, 3D position, attached script). If no scene is open or nothing is selected, the request says so instead of inventing context. Each queued turn step makes one model request; there is no classification request and no manual category control. The root `AGENTS.md`, when present, is captured at submission as bounded project conventions and included as a non-authoritative prompt section; a missing, oversized, or invalid file is reported and ignored without failing the turn. The tool payload is assembled from the active tool mode and real availability: editor/hybrid includes the typed editor transaction and specialized recipes, debugger tools, and asset/device tools; workspace/hybrid includes the workspace file, search, git, and headless tools. The prompt tells the model not to claim a change unless a tool result reports success, and to reply in plain text without Markdown decoration. Screenshots and user-supplied visual JSON are not supported. These inputs are sent to the configured Tiiny endpoint; the assistant only inspects the paused debugger when a debugger session is active.

The built-in Godot-oriented system prompt and `ResourceToolLibrary` are in `editor/tiiny_ai_dock_source.h`. Optional additional instructions can be set under **Tiiny AI > Advanced > System Prompt Extra**. The request timeout is also configurable there.

## Next work

The persistent job manager is in progress. Its experimental panel, chat submission and reviewed tree fixture are available, while portable storage, device coordination and full recovery acceptance remain unfinished; see [plan item 02](../../plan/work-items/02-integration-job-manager.md).

The subsequent workspace milestone is a typed, validated scene operation: inspect a selected node, add a node, create and assign a compatible resource, and group the change into Godot's undo/redo system. Subsequent work can add animation, physics, materials, generated 3D assets, audio, and live debugging. The assistant should prefer those native operations before reaching for GDScript.

Model-role selection does not itself implement a generation workflow. Image-to-3D, material, music, speech, sound-effects, and debugger tools still need adapters, validation, and testing. Likewise, a generated image is not automatically a seamless texture or a complete PBR material.

## Verification

Run from this checkout after building:

```sh
python3 integrations/tiiny/tests/check_model_configuration.py --editor-smoke
python3 integrations/tiiny/tests/check_model_configuration.py --http-smoke --displayed --report /tmp/tiiny-story01-displayed.json
python3 integrations/tiiny/tests/check_model_configuration.py --live-inference --report /tmp/tiiny-story01-live.json
python3 integrations/tiiny/tests/check_workspace_tools.py
python3 integrations/tiiny/tests/check_workspace_bakeoff.py
python3 integrations/tiiny/tests/check_workspace_displayed.py
python3 integrations/tiiny/tests/check_workspace_coding_live.py
```

The first command uses isolated settings/HOME and fake inference/SDK boundaries. It covers parsing, model planning, startup failures, malformed tools, script validation, no overwrites, context recovery, native dialog cancellation/late responses, ordinary resource/node creation, and owned SDK child cleanup. The second runs a loopback HTTP service, exercises actual request timeouts, PNG decoding/import and polygon requests, runs a fixture scene, checks Output, and captures displayed settings/chat windows. `check_workspace_tools.py` runs the pure and editor workspace fixtures (path confinement, hash-guarded writes/patches, commit-time conflict interleavings, git filtering, command gating, dirty-scene/mode/card editor checks); `check_workspace_bakeoff.py` solves ten fixed tasks through both tool families and verifies recovery; `check_workspace_displayed.py` captures the workspace and hybrid mode labels in a real X11 editor; `check_workspace_coding_live.py` is a gated real-device tool-choice trace. `check_task_catalog.py` requires a task-specific assertion in the referenced test for every supported task. See [test instructions](tests/README.md) for backend selection and diagnostics.

`--live-inference` explicitly uses the connected Tiiny, picks an already-warm compatible coding model in temporary editor settings, sends chat and polygon requests, validates the saved polygon, and checks that model residency is unchanged. It tests image generation only when an image model is already warm; otherwise that adapter remains experimental. It never invokes model-management Apply. `--live-readonly` instead checks live inventory and Check Config without inference. `--live-apply` performs one explicitly selected download-only Apply with temporary settings and verifies progress, completion, and an unchanged warm set; the downloaded model remains on the device. Real generator quality remains separate acceptance work under story 09.

Chat accepts one function call per response, up to four tool rounds per turn. Invalid envelopes, empty/repeated IDs, and malformed arguments are rejected before dispatch; unknown tools return matched errors. Completed tool results appear immediately and remain in context after a failed continuation. Nothing automatically retries or rolls back completed files. Error handling avoids copying HTTP response bodies into Output.

Known baseline limitations include dummy-display popup warnings under headless testing. The former MultiplayerPeerExtension/WebRTCDataChannelExtension required-virtual diagnostics are fixed: both extension base classes are now registered as virtual classes, so the editor help cache no longer instantiates them when deriving class-reference defaults. The separate invalid-script test deliberately expects one parse diagnostic. Passing Tiiny checks do not imply an otherwise diagnostic-free upstream Godot build. Earlier reports remain in [baseline evidence](../../plan/evidence/01-baseline.md) and [protocol evidence](../../plan/evidence/01-chat-protocol.md).
