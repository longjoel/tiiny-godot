# Workspace acceptance scenarios

These scenarios supplement each work item's checkboxes. They are proposed acceptance tests, not verified capabilities. Use a disposable fixture project and reset its scene/files between runs. Test the executor with fixed requests first, then evaluate model planning separately. Several Godot solutions can satisfy an intent: judge required outcomes and constraints rather than exact generated names or prose.

| ID | Request and fixture | Observable acceptance | Item | Automation |
| --- | --- | --- | --- | --- |
| WS-01 | Select a CharacterBody2D and ask “Add a rectangular collision shape, 32 by 48.” | Exactly one appropriate CollisionShape2D with owned RectangleShape2D is created, its size is correct, the scene persists on reopen, and one undo/redo removes/restores the change. No script created. | 05–08 | Fixed executor input plus editor integration; live-model planning evaluation separately. |
| WS-02 | Issue WS-01 against an incompatible parent or a node deleted since inspection. | Explicit target/compatibility failure; no partial nodes, resources, or undo entry. A newly selected node is never substituted silently. | 05–07 | Deterministic negative tests. |
| WS-03 | Ask “Make this floor slippery” on a suitable physics body. | A compatible PhysicsMaterial is assigned with the intended friction; unrelated objects sharing the original material are unchanged unless included in the request. Undo restores the original assignment. | 11 | Resource/scene assertions plus runtime physics check with tolerances. |
| WS-04 | Ask “Make this torch flicker” in a scene containing a supported light. | Native animation tracks target existing writable properties; an animation plays with bounded light variation and no new GDScript. Existing animations are preserved. Undo restores the fixture. | 11 | Editor structure checks and sampled runtime values; visual review supplements these checks. |
| WS-05 | Ask “Fade this panel in over half a second” in a fixture with a Control. | Supported native animation changes the intended opacity, reaches its final value within tolerance, preserves unrelated properties, and is undoable. | 11 | Deterministic animation sampling and editor test. |
| WS-06 | Ask for an image with a configured warm image model. | Correct role is invoked, a valid image is saved to a new project path and imported, and chat links to that artifact. Existing assets are not overwritten. | 09 | Fake inference response in ordinary CI; real-device smoke test separately. |
| WS-07 | Select Image, ConvexPolygonShape2D, and an unsupported resource type in Create New Resource. | The prompt is enabled only for implemented recipes. Blank input follows ordinary creation. | WS-08 | Ask for a textured prop from a reference image. | Each supported image-to-3D/import stage records its inputs and actual outputs; resulting mesh/material resources resolve in Godot. | WS-09 | Fail texture generation after a successful shape stage. | Chat identifies the failed stage and saved intermediate shape; retry resumes from that artifact rather than regenerating or claiming the whole asset completed. | 09, 10, 13 | Fault-injected workflow test. |
| WS-10 | Ask for a spoken line or instrumental loop. | Correct audio role is used; the output imports and plays, has valid duration/channels, and is reported as speech or music accurately. Seamless looping is verified separately, never inferred from the model name. | 13 | Fixture audio validation plus real-device semantic/audio review. |
| WS-11 | Pause a fixture at a breakpoint and ask why the enemy is stationary. | Correct session/frame and relevant live properties are read; edited-scene defaults are not substituted for runtime values. Continuing execution invalidates stale pause context. | 12 | Controlled debuggee integration and scripted pause/resume. |
| WS-12 | Ask to set a breakpoint on an existing script line, then delete/rename that script. | Valid breakpoints appear in debugger UI and affect execution; stale locations produce errors rather than being applied to another file. | 12 | Debugger integration test. |
| WS-13 | Switch scenes or edit a target between planning and execution. | Revision/identity checks reject a stale plan or explicitly re-inspect and revalidate. No mutation reaches the wrong scene. | 06–08 | Deterministic interleaving test. |
| WS-14 | A parallel coding agent modifies a file before the assistant applies a file operation. | Existing content is preserved; conflict is reported or a fresh version is read before a supported operation. No blind overwrite. | 07, 08 | Filesystem concurrency test; no second agent needed. |
| WS-15 | Model returns unknown tools, malformed JSON, incompatible types, repeated calls, or too many steps. | Unsupported requests do not mutate the project; bounded execution returns useful errors; a later request still works. Retried mutation cannot create duplicate objects unnoticed. | 01, 07 | Fake-model protocol suite. |
| DEV-01 | Request a specialized job that needs space while coding and user warm models are loaded. | Coding model is never deliberately evicted. Eligible models are swapped; requested warm state is restored after the job or restoration failure is explained. | 03, 10 | Simulated scheduler plus optional hardware run. |
| DEV-02 | Disconnect or exhaust storage during download/load/inference. | UI stays responsive; device state is marked unavailable/partial; completed artifacts are preserved; reconnect does not duplicate jobs or falsely declare readiness. | 03, 04, 10 | Fault injection plus selected hardware checks. |
| DEV-03 | Configure a text-only model with a screenshot, or an image model as the coordinator. | Incompatible combinations are rejected before inference or device mutation; capability and role requirements are explained. | 04, 07 | Catalog fixtures and selection tests. |

For live-model evaluations, run several paraphrases of each request and record model ID/build, service version, settings, tool trace, elapsed time, final scene/resource state, and review findings. Report success rates and failures instead of requiring identical prose or claiming all future runs will succeed.

## Job manager foundation (item 02)

| ID | Scenario | Observable acceptance |
| --- | --- | --- |
| JOB-01 | Append create tree, then attach tree. | Only one job runs; validation/import completes before attachment. The attachment uses the explicit tree artifact and intended scene. |
| JOB-02 | User and script append while another job runs. | Manager assigns durable sequence numbers; all new work goes to the tail and no execution overlaps. |
| JOB-03 | Restart during execution or asset promotion. | Order and stop/pause state survive; unknown effects are reconciled before dispatch; no blind replay or duplicate asset. |
| JOB-04 | Tree creation fails, then retry or explicitly skip it. | Attachment stays queued; retry happens first at the stopped position. Skipping cannot substitute a missing artifact; downstream input checks still apply. |
| JOB-05 | Pause or cancel current work. | Pause prevents the next job starting; cancellation resolves the current worker and stops dispatch. Completed effects remain visible. |
| JOB-06 | Invalid submission, timeout, invalid output, stale target or conflicting destination. | Invalid submissions are not accepted; execution failures stop the queue with useful diagnostics, and no unvalidated output is promoted. |
