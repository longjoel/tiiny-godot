# Parked ideas

Capture promising ideas here without interrupting the active item. Each entry should say what it enables, which existing item it relates to, and what evidence would justify moving it into the sequence. An entry is not authorization to implement it.

The sequenced backlog already includes animation, debugging, and multi-model assets. Additional integration ideas below remain parked until their related item is active:

- **Promoted into stories 14–17:** generic typed editor primitives, first-class script behavior/attachment/save, catalog v2/composed-task tests, and specialized authoring recipes. These are no longer parked ideas; see the work-item sequence.

- **Workspace recipe memory** (06, 08): persist successful operation recipes and resource provenance so the assistant can adapt a known Godot workflow. Promote after typed execution and repeatable acceptance tests exist; distinguish cached recipes from stale scene state.
- **Project retrieval on Tiiny** (04, 06, 27): use embeddings/reranking to find relevant scenes, resources, and documentation. Promote after a baseline demonstrates missed context; compare retrieval accuracy and latency against simple project search. Index updates must follow edits/imports. The device already exposes a vault (`tiiny vault add/index/query/ls`) and has five indexed daily conversation files; `Qwen3-Embedding-0.6B` is installed but not loaded and uses 2 NPU units. Indexing requires an embedding model (the CLI says so explicitly), and a `vault query` without one was still waiting on `/kb/retrieve` when the 60-second probe was stopped. The structured Godot class reference is 833 XML files / 9.8 MB and is already served exactly and offline by `lookup_docs`; do not duplicate it in the vault. Vault is a better fit for a small curated corpus of project notes, workflow recipes, tutorials, or prior decisions, with bounded cited results. A pilot should compare vault retrieval against `search_text` and `lookup_docs`, measure embedding load/query latency with the coding model warm, and start with 10–50 files because there is no bulk-ingest path yet.
- **Device-aware job telemetry** (02, 09): incorporate SDK task status and measured load/inference time into scheduling and visible progress. The installed CLI exposes `tasks ls` and `bench`; verify their actual behavior before relying on them. Promote when the basic queue is reliable.
- **Asset feedback loop** (08, 12): render generated resources in a controlled Godot scene and let a vision model propose bounded changes. Promote after asset import and workspace edits are validated. Judge both scene correctness and user-visible quality.
- **Vision classification of textures and rendered scenes** (18, 27): the image role is text-to-image and cannot inspect an image; the coding role accepts `Image-Text-to-Text`. Verified on the device with `Qwen/Qwen3.6-35B-A3B` (`supports_vision: true`): an OpenAI-style `image_url` content part with a base64 PNG returned a correct description (“yellow circle centered on a red square, blue background”). Add a vision path only after the chat builder can attach a downscaled PNG to a model request, capability detection is available from the model type, image data is redacted from traces/logs, and the deterministic `find_assets` metadata fallback is in place. Useful for “is this texture a brick wall or a player?” and rendered-scene review; not a substitute for the inventory.
- **Interactive plan wizard** (23, 20, 02, 31): today `submit_plan` is a single request and the 1–3 task plan queues immediately; the user can only intervene after a task fails (Fix/Skip/Cancel/Ask planner). An in-editor wizard would let the coding model propose a bounded plan, then let the user edit task briefs, add constraints, reorder or drop tasks, and ask for one bounded revision before explicitly choosing **Run plan**. That needs a draft state that is not yet a queue job, editable task cards, a bounded revision loop, and a transition into the existing plan-tree contract without changing its serial/deferred-join semantics. Evidence to promote: a displayed editor capture of draft → edit → revise → run, plus a deterministic fixture proving no task dispatches before approval and that revisions keep task IDs, limits, and dependency order valid.

- **Context and prompt-cache budgeting** (06, 09): reuse stable project context where the runtime supports it and measure latency across context sizes. Promote only after measuring actual SDK/runtime support; avoid assuming a cache exists.
