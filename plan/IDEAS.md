# Parked ideas

Capture promising ideas here without interrupting the active item. Each entry should say what it enables, which existing item it relates to, and what evidence would justify moving it into the sequence. An entry is not authorization to implement it.

The sequenced backlog already includes animation, debugging, and multi-model assets. Additional integration ideas below remain parked until their related item is active:

- **Generic scene node and property recipes** (06, 11): the 100-task catalog shows the largest gap is ordinary editor composition: adding Camera2D/3D, lights, UI controls, meshes, bodies, particles, and setting common properties. Add a reviewed recipe family that creates one typed node with validated initial properties and one undo action, rather than exposing arbitrary property writes. Highest-leverage test batch: `2D-005`–`2D-019`, `3D-051`–`3D-062`. Promote when each recipe has schema validation, ownership checks, undo/redo, and a supported-target availability rule.
- **UI composition recipes** (06, 11): the catalog has no dedicated UI path (labels, buttons, progress bars, menus, anchors, themes). Add focused recipes for common HUD/menu structures instead of generic Control tree construction. Test at 320px/600px and with real input/signal wiring.
- **3D material/lighting/camera recipes** (06, 11, 13): missing material creation, PBR property edits, environment/fog, camera creation, and light creation account for most 3D gaps. Add typed recipes with target-aware availability and explicit unverified PBR/texture flags where the value is inferred.
- **Animation/tween recipes** (06, 11): generic rotation, door-open, camera tween/orbit, and sprite-frame workflows remain missing beyond the torch-flicker recipe. Add a small native animation recipe family and validate playback structurally before adding displayed checks.
- **Physics body/joint/layer recipes** (06, 11): the catalog reveals missing StaticBody/CharacterBody/RigidBody/Area creation, collision polygons, joints, layers, and one-way platforms. Add recipes that validate class/property compatibility and preserve existing user resources.

- **Physics property recipes** (06, 11): add reviewed recipes for common physics edits such as gravity scale, motion mode, damping, and collision layers instead of exposing generic property writes. Gravity requests currently have no native recipe; the model should explain the limitation. Promote with story 11's animation/physics workflows and test each recipe with one undo group, stale-scene rejection, and class/property validation.
- **Attach generated scripts through typed scene edits** (05, 06, 07): let the assistant create a GDScript and assign it to a selected node, optionally creating the node and setting a few validated properties, in one reviewed undo action. This is the missing follow-up observed after the DVD-bounce smoke test: `create_gdscript` writes the file, but there is no tool to attach it to a scene node. Implement it as an executor recipe, not an append-job or raw property mutation: require a saved clean scene, bind the expected base/session revision, validate the script resource and node ownership, record one undo action, and mark the scene dirty without saving automatically. Promote after story 05 inspection and story 06's transaction executor/undo gate exist; evidence should include a script assignment with undo/redo, stale-scene rejection, and an inherited/instanced-node rejection or documented support.
- **Workspace recipe memory** (06, 08): persist successful operation recipes and resource provenance so the assistant can adapt a known Godot workflow. Promote after typed execution and repeatable acceptance tests exist; distinguish cached recipes from stale scene state.
- **Project retrieval on Tiiny** (04, 06): use embeddings/reranking to find relevant scenes, resources, and documentation. Promote after a baseline demonstrates missed context; compare retrieval accuracy and latency against simple project search. Index updates must follow edits/imports.
- **Device-aware job telemetry** (02, 09): incorporate SDK task status and measured load/inference time into scheduling and visible progress. The installed CLI exposes `tasks ls` and `bench`; verify their actual behavior before relying on them. Promote when the basic queue is reliable.
- **Asset feedback loop** (08, 12): render generated resources in a controlled Godot scene and let a vision model propose bounded changes. Promote after asset import and workspace edits are validated. Judge both scene correctness and user-visible quality.
- **Context and prompt-cache budgeting** (06, 09): reuse stable project context where the runtime supports it and measure latency across context sizes. Promote only after measuring actual SDK/runtime support; avoid assuming a cache exists.
